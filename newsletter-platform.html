← Back to selected work ARCHITECTURE CASE STUDY / 2023 — PRESENT

Scaling a newsletter platform while cutting backend cost by nearly 50%

The existing path struggled as more brands and markets came online. I used a measured Core API prototype to make the case for a simpler architecture, then helped turn that decision into an efficient production platform.

Condé Nast · Software Engineer III · High-level technical account

01 / THE CONSTRAINT

Growth exposed
the cost of complexity.

The platform needed to onboard more markets and brands without multiplying pods and managed-service cost.

~30 RPSold API instability observed
6 podsup to, per region, before redesign
>200 RPSoptimized API prototype in one pod
512 MBprototype pod memory allocation

The original Core API was not optimized for memory or CPU use. It became unstable around 30 requests per second; even with up to six pods running in each region, OOMKilled events still occurred. Redis held the full subscription dataset rather than being limited to repeated reads. SQS, Lambda, and Kafka added operating cost around an API that needed more efficient code.

03 / DECISIONS & OWNERSHIP

An evidence-led
architecture change.

Each removed component was backed by a concrete change in application capacity or responsibility.

01 / PROVE

Start with the API

I built a memory- and CPU-optimized Core API prototype that served more than 200 RPS in one 512 MB pod, then presented the result to the team and director.

02 / SIMPLIFY

Remove unnecessary ingress

That result supported removing SQS and Lambda ahead of the API. I narrowed Redis use to caching repeated database calls instead of retaining all subscription data.

03 / REPLACE

Retire Kafka delivery

I replaced the costly Kafka connector with a Node.js service that watches a queue collection and orchestrates messages to downstream systems in a single 512 MB pod.

04 / EXTEND

Handle market consent jobs

The scheduler pulls consent data from multiple sources and S3. Jobs transform records and submit them to the Core API before the orchestrator passes them downstream.

The tradeoff

The simpler deployment put more of the queue watching and downstream handoff in our Node.js code. We accepted that responsibility because the measured workload fit within a small pod and the new path reduced operating cost.

04 / OUTCOME

Lower cost,
room to grow.

Capacity measurements informed the design; the production platform now supports a larger operating footprint.

Nearly 50%lower backend cost from the full architecture overhaul
50M+subscriber records supported
~400 RPSobserved production peak during major events
~180 MBtypical job-runner memory within a 512 MB pod

The >200 RPS figure is from the Core API prototype; the ~400 RPS figure is an observed production peak. The cost reduction reflects the full backend overhaul, including service removal and code optimization.
